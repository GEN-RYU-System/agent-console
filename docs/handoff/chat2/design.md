## 0. 事実（recon より）
- 作業中（busy）に、括弧付きで貼って 2秒後に Enter を送ると、今の作業は止まらない。文章は順番待ちに入り、同じターンの中で処理される（recon C-1、公式 interactive-mode 357-369）。
- 許可の確認が出ているときに、同じ形で貼って Enter を送ると、4回とも「1. Yes」が押され、命令が実行された。貼った文章は、どこにも入らなかった（recon C-2）。
- 許可の確認が出ているときに、貼るだけで Enter を送らなければ、何も起きない。ただし、文章は消える（recon C-3）。
- `claude agents --json` の状態は、画面より 1〜4秒遅れて「待ち」になることがある。1回の取得に 0.8〜11秒かかる（recon C-4、D）。
- 以上から、Enter の直前にもう一度判定しても、許可の確認が出た瞬間を確実には見分けられない。
- v0.3.7 の名前の予約は、作業中は予約し、手が空いたらサーバーが端末に書く（server/hub.ts:172-181 applyRename、hub.ts:184-203 flushPendingRenames、pollAgents の hub.ts:122 から呼ぶ）。
- recon の道具 run.cjs:35 は、node-pty へ直接 `\x1b[200~…\x1b[201~` を書いた。C-1 では、それで正しく順番待ちに入った。サーバーから括弧付きで書く方法は、実機で動いている。

## 1. 方針
- 作業中は、端末に何も書かない。チャットで送った文章は、サーバーのメモリで「予約」として持つ。手が空いたら、サーバーが1件ずつ端末に書く（v0.3.7 の名前の予約と同じ作り）。
- 画面の「送る」は、いつでも「予約に入れる」だけにする（経路を1本にする）。手が空いていれば、入れた直後の flush ですぐ送られる。
- 「よく使う指示」「変更」「部品」の即時送信（便1の send-check→paste）は、今のまま残す。触らない。

## 3. 仕組み
### 3-1 サーバー（hub）
- `chatQueue: Map<アプリのセッション id, ChatQueueItem[]>` をメモリに持つ。`ChatQueueItem = {id, text, createdAt, state: "queued"|"sent", sentAtSeq?}`。
- 送った後の待ちとして、`chatSentGuard: Map<id, {awaitingActivity: true, sentSeq}>` を持つ。K3 の (a) か (b) を観測したら消す。
- 定数は `CHAT_QUEUE_MAX = 10`。
- `POST /api/sessions/:id/chat/queue {text}`
  - 本文の検査は、便1の send-check と同じ関数を使う。
  - stopped は 409。上限を超えたら 409。
  - 予約に足して、すぐに `flushChatQueue(session)` を1回呼ぶ。`{id}` を返す。
- `DELETE /api/sessions/:id/chat/queue/:qid`: queued の予約を取り消す。sent は消せない（409）。
- `GET /api/sessions/:id/chat` の応答に、`queued: [{id, text, createdAt, state, sentAtSeq}]` を足す。
- `flushChatQueue(session)`
  - 呼ぶ場所は、pollAgents の flushPendingRenames と同じ所（hub.ts:122）と、予約を足した直後。
  - 同期の印 `flushing` で、同時の実行を防ぐ。
  - 送る条件:
    - idle かつ待ちなし（今の inputVerdict）。
    - `chatSentGuard` が無い。
    - queued が1件以上ある。
  - 送り方:
    - 古い1件の state を、同期で "sent" に変える（await の前）。
    - `hasClaude` なら `\x1b[200~`＋text＋`\x1b[201~` を書く。素のシェルなら text をそのまま書く。
    - `submitDelayMs`（設定 agent-console.config.json:17）待つ。
    - 待った後に、`session.exited` と取り消しを確かめる。どちらかなら、Enter を送らない。
    - どちらでもなければ `\r` を書く。
    - `sentAtSeq` に、その時点の activity の最後の seq を入れ、chatSentGuard を立てる。
- 予約の「送信済み」は、`sentAtSeq` より後の seq で role=user の記録が届いたら、予約から外す。外す判定は、activity に記録が足された時（サーバー内）に行う。
- K3 の (a) は、BreakTracker の前回の status で判定する。
- 自動の再送はしない（送った後に失敗しても、予約には戻さない）。

### 3-2 画面（ChatPane）
- 「送る」は、いつでも `POST /chat/queue` を呼ぶだけ。
- 予約は、会話の一番下に送る順に並べる。各予約に Badge（予約中／送信済み）を付ける。予約中には「取り消す」の Button も付ける。上に「アプリを再起動すると予約は消えます」の文を出す。
- 許可・質問の待ちのときは、便1の案内（端末で確認が出ています）を出したまま、予約はできる。
- 文言は ja.json に置く。色・余白は SA のトークンを使う。

## 4. SSOT
- 予約の正本は、サーバーのメモリ（hub）の1か所。画面はその写しを出す。
- 会話の正本は、今の記録（dataDir/activity/）のまま。

## 5. 安全
- busy・waiting・unknown の間は、端末に何も書かない（K2）。
- 1件送った後は、Claude が受け取ったことを観測するまで、次を送らない（K3）。状態の遅れで、作業中の Claude に Enter を送ることを防ぐ。
- 判定と Enter の間の約2秒の窓は、便1・v0.3.7 と同じ。idle で、送った直後の待ちも無い状態から始めるので、この窓で許可の確認が出ることはない。
- 自動の再送はしない。

## 6. 代替案
- 作業中に、そのまま貼って Enter を送る（公式の順番待ち）: 許可の確認と重なると「Yes」が押される（recon C-2）。判定の取り直しでは防げない（recon C-4、D）。不採用。
- 作業中は貼るだけにし、Enter は手が空いてから送る: 許可の確認の間に貼った文章は消える（recon C-3）。不採用。
- 送る役目を画面に持たせる（第1版）: 画面が閉じていると送られない。複数のタブと60秒の戻しで、二重に送るおそれがある（Fable の H1・H2）。不採用。
- 予約をファイルに保存する: YAGNI。不採用。

## 7. リスク
- 作業が長いと、予約がなかなか届かない: 予約の印で見えるようにする。
- 【未確認】サーバーから括弧付きで書いたときに、長い本文（32KiB 近く）を `<pasted_content>` に包む動きが、xterm.paste() のときと同じか（L1）。工程0で1回確かめる。違えば、本文の上限を下げる。

## 10. 実装時の決め（Fable 第2回審査の指摘を設計者が確定）
