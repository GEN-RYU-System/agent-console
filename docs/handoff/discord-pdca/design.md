# design: Discord の不具合報告から agent-console が対応を回す（discord-pdca）

> この文書は何か：Discord の不具合チャンネルに書かれた報告を、AI が受け取って調べ・直し・効果を確かめるまでを自動で回す仕組みの設計図です。

- 親の仕様: Sales Anchor の `docs/specs/discord-ops-intake/README.md`（Discord から AI 保守へつなぐ仕組みの表紙。今の対象は監視の通知だけなので、不具合チャンネルをこの子として載せる親→子のリンクは便0 の Sales Anchor の文書の PR で足す）。
- 関係する ADR（Sales Anchor。衝突は無い）:
  - ADR-1029（マージ前の Opus 審査の強制）: Discord 発のセッションは PR のマージをしない（K13・§14-5）。マージは今までどおり人の手順と ADR-1029 の審査を通る。
  - ADR-1033（会話の合意で許可を出す同意票）: Discord 発のセッションは同意票を使わない・作らない。外への通信の道具（WebFetch・WebSearch）は K13 で道具ごと外す。外への送信（curl・wget）と鍵の読み出し（`security`）は名前の形の拒否では塞げないので、許可した行き先のほかへの送信と、秘密の置き場・Keychain の読み出しを、囲い（サンドボックス）の作りで塞ぎ K17・K11 で確かめる（許可した行き先へは送れる弱さは ADR-1039 に書く）。置き場の読み取りの拒否は K13 に残す。マージ・ac-reserve・ac-routine の名前の形の拒否は補助（§2 K13）。
  - ADR-1034（権限の足し引きと台帳）R4: この設計は見張り（フック・関所）を弱めない。足す権限は §4-5 の起動の引数だけで、settings の常設の許可は足さない。
  - ADR-113（terminal / handoff の2つの型）: この設計は handoff（設計の持ち込み）で渡す。ADR-113 の「モード強制」に従い、冒頭の front-matter に `mode: handoff` を書いた。実装はこの設計の How を権威として、便ごとに渡す。

## 1. 目的（PO の言葉）

- 2026-10-21 PO:「claudeとDiscordを繋ぐのではなくagent consoleとdiscordを繋いでほしい」
- 流れ:
  1. 不具合報告のチャンネルに投稿する。

## 3. 対象と対象外

### 3-1 対象

- agent-console に次を足す。
  - Discord の受け口（1つの部品で、受付チャンネルと誤り報告チャンネルを読む）
  - 種類ごとの順番待ちと、不具合の件の回（測定と合否）
  - 報告（Webhook で報告チャンネルへ）
  - 全停止の読み取り（既存の `halt_all` を見る。新しいスイッチは作らない）
  - 測定の予約をサーバーが作る仕組み（`ac-case measure`）
- Sales Anchor の保守 API に、人の報告の入口を2つと、回の記録の欄を足す（§4-9）。
- 予約と定期実行に、1時間の関門と予約の監査記録を足す。
- Discord 発のセッション用に、ツールを起動の引数で絞った役割 `discord-case` と、測定用の役割 `discord-measure` を足す。
- 落ちたら起こし直す見張り役を足す。
- Sales Anchor 側の文書:
  - ADR-1039 を新しく立てる（便0 で Proposed、便2 の前に Accepted）。ADR-1009・ADR-1012・ADR-1025 との関係を書く（§4-8）。
  - Discord 発のセッションに渡す指示書を1つ足す（正本は1か所、§4-5）。
  - ADR-1025 の設計（S:docs/handoff/analysis-error-report/design.md §4-4）の古くなった記載を直す（§4-8）。

### 3-2 Fable と確認した安全の条件（本設計で守る）

1. 外からの入口（受け付け用のポート）を開けない。agent-console から Discord へ読みに行く一方向だけにする。
2. 投稿の本文はデータとして囲んで渡す（K10）。

6. Discord 発のセッションは、できることを起動の引数で絞った役割で動かす（§4-5、K13）。指示書だけに頼らない（S:ADR-1012 Why「指示（プロンプト）は防壁にならない」）。
7. ADR-1009 を退役させる（§4-8）。
8. ボットの権限は、読む2つのチャンネルの「見る」「履歴を読む」だけにする（§4-1）。

- 誤り報告の件の中身（指示書・専用の鍵・照合・再解析）。ADR-1025 の範囲で、本設計は受け口・順番待ちだけを共通にする。全停止は共通にする（§14-7）。

## 4. 変更前 → 変更後

### 4-1 Discord の受け口（新しい部品 `server/discord-intake.ts`）

- **変更前**: agent-console は Discord とつながっていない（R§4）。誤り報告の受け口は設計だけあり、作っていない（R§12）。
- **変更後**:
  - `dataDir/discord-intake.config.json`（§4-6）の、チャンネルごとの `enabled` が true で、Keychain にボットのトークンがあるときだけ動く。既定は両方無効。トークンが無い・読めないときは受け口だけを無効にし、サーバーの他の動きは続ける。
  - 読み方は ADR-1025 と同じ（S:docs/handoff/analysis-error-report/design.md:67）: 30秒ごとに、有効なチャンネルを1つずつ Discord の REST（`GET /channels/{id}/messages?after=<そのチャンネルの最後の id>&limit=100`）で読む。429 と待ちの指示に従って待つ。常時接続（Gateway）は使わない（§5 案A）。
  - 読む通信は1つの部品で行い、チャンネルごとに「拾う条件」と「種類」を設定で持つ。
    - 受付チャンネル（種類 `bug`）: guildId が設定の値と同じ。channelId が受付チャンネルと同じ（スレッドは channelId が違うので出てこない）。author.bot が false で webhook_id が無い。author.id が許可表にある。メッセージの種類が設定の `allowedMessageTypes` に入っている（システムの投稿を拾わないため。0-3 の実物で、PO の普通の投稿は 0、返信は 19、ピン留めの知らせは 6（本文は空）を返した。値は `[0, 19]`。ボット・Webhook の投稿の種類の値は試していない【未確認】が、それらは author.bot と webhook_id の判定で先に捨てる）。種類で捨てた投稿は `dropCounts.messageType` に数える。
    - 誤り報告チャンネル（種類 `error-report`）: ADR-1025 の決まりのまま。webhook_id が決めた webhook と同じで、本文が `ER-` ＋6桁に合うものだけ（S:design.md:68・:70）。
  - id は数字の文字列なので BigInt で比べる。0-3 で、返る順は `after` を付けても id の減る順（新しい順）で、`after` は指定した id 自身を含まないと確かめた。そのため受けたページごとに小さい順へ並べ直し、チャンネルごとの `lastSeenId` より大きいものだけを、小さい順に受ける。
  - **初めて読むとき**（`lastSeenId` が無い）は、読んだ中で一番大きい id を `lastSeenId` にするだけで、過去の投稿は受けない。
  - 読んだ100件がちょうど100件だったときは、続きがある。同じ周回の中で `after` を進めて続きを読む。1周回で読むのは1チャンネル5回（500件）まで。超えたら「取りこぼしの可能性」を報告チャンネルに1件送り、次の周回で続きから読む。0-3 で、`after` と `limit` でページを送ると、各ページは `after` より後の投稿のうち古い方から `limit` 件で、続けて読むと全部そろった（取りこぼし0件）。次のページの `after` は、受けたページの一番大きい id にする。
  - 条件を満たさない投稿は捨て、理由ごとの件数を手元の `dropCounts` に足す（障害記録には書かない。§4-6）。本文は残さない。
  - 投稿の本文は手元に残さない。残すのは id・時刻・投稿者 id・本文の文字数だけで、本文は Discord が正本。
- 本番ボットとの照合（U1）: 最初の読み取りの前と、その後1時間ごとに、ボット自身の id を `GET /users/@me` で読む。本番アプリの id（R§6。値はこの公開の文書に書かない）と同じなら、受け口を止めて報告チャンネルに知らせる。便0 で最初に確かめる。
- ボットが見えるチャンネルを受付チャンネルと誤り報告チャンネルの2つだけにするのは、PO が Discord の画面で行う（§7 0-7）。
- 負荷: ADR-1025 G6（CPU の1日平均の増分1%未満・メモリの増分50MB未満。S:docs/specs/analysis-error-report/kgi.md:16）を、この共通の部品で測る（便2 の受入）。

### 4-2 種類ごとの順番待ちとセッションの起動

- 受けた投稿は、種類ごとの順番待ちに入る。枠は種類ごとに1つ（PO 2026-10-21「1」）。
  - `bug`: 不具合の件。本体・測定の両方を同じ枠で数える。
  - `error-report`: 誤り報告の件。ADR-1025 の決まり（同時1・1時間に6つ・同じ番号は1回。S:design.md:72）をそのまま守る。
- **不具合の枠が空くのは、今のセッションが閉じたときだけ**（H-A）。kept・長時間では空けない。誤り報告の枠で kept をどう扱うか（空けないと ADR-1025 G2b の5分を外れうる）は、ADR-1025 の便4 の設計で決める。本設計の便2 では、誤り報告の枠は今の ADR-1025 の決まりのまま動かす。
  - 閉じる: 10分の**続けての** idle（routine-closer と同じ基準。R§2）で、サーバーが `sessions.close`（A:server/index.ts:94・sessions.ts:509）を呼ぶ。閉じたら出来事 `closed` を書く。
  - kept（`NEEDS_DECISION:`・`BLOCKED:`・60分の入力待ち・最後の返答が読めない（no-reply））: 閉じずに枠を持ったまま、出来事 `kept`（`reason` に理由）を書き、報告チャンネルへ「判断待ち」を出す。PO が画面のそのセッションで答えれば、セッションは続きを進め、最後の返答に `NEEDS_DECISION:` も `BLOCKED:` も無いまま10分 idle になったら閉じる。PO が画面でそのセッションを閉じても枠は空く。
  - 開いてから8時間たった: 閉じずに枠を持ったまま、報告チャンネルに「長くかかっています」を出す（以後8時間ごとに1回）。
  - 不具合の順番待ちは、kept の間は進まない。待っている件の数を「判断待ち」の知らせに添える。
  - 見張りは受け口の部品が自分で持つ。routine-closer は kept のあとは見なくなる（A:server/routine-closer.ts:70-74）ので、そのまま使うと kept のセッションが見張りから外れる。判定の関数（idle の続き・`NEEDS_DECISION:`/`BLOCKED:` の読み取り。:13・:56-57・:76-85）は共通の関数として取り出して両方から使い、kept のあとも見続けるのは受け口の側だけにする。定期実行の今の動きは変えない。
  - 見ているセッションの id と状態は `discord-intake.json` に書き、サーバーを起こし直したら読み直す。読み直したとき、そのセッションが `claude agents --json` に無ければ、閉じたとみなして出来事 `closed`（`reason: 'lost'`）を書く。
- 測定の予約が時刻になったとき（M-5）: 予約の起動は、その種類の枠を通す。枠が空いていれば開く。空いていなければ、その種類の順番待ちの**先頭**に入れる（新しい件より先に開く）。
- 開くときは `launchAndSend`（R§3）を使う。
  - `bug`: 役割は `discord-case`。セッション名は `不具合 10/21 12:34`（投稿の日本時間。40字以内）。
  - `error-report`: 役割と指示文は ADR-1025 の決まり（S:design.md:73）。セッション名は報告番号を含む（S:kgi.md:12）。
- 依頼文はサーバーが決まった型で組み立てる（§4-5）。不具合の本文は Discord から読み直し、4000字で切る。
- `bug` の上限:
  - 順番待ちは20件まで。超えた投稿は受けず（`dropCounts.queueFull`）、報告チャンネルへ知らせる。
  - 1日（日本時間0時区切り）に新しい件として開くのは10件まで。次の回・測定は数えない。超えた分は翌日に回し、知らせる。
- 開けなかったとき（L-3。`launchAndSend` の答え。A:server/launch.ts:18,:103-113）:
  - `full`（同時セッションの上限16、R§3）・`not_ready`・`failed`: 1分おきに5回までやり直す。`not_ready` と `failed` でセッションが作られていれば、やり直す前にそのセッションを閉じる（枠を2つ使わない）。5回とも開けなければ、出来事 `launch_failed`（`reason` に答えの値）を書いて知らせ、その件は順番待ちの先頭で止める（後ろの件も進まない）。PO が画面の「やり直す」で再開する。知らせには kept の数を添える。
  - `cwd_invalid`: 設定の誤りなのでやり直さない。すぐに `launch_failed` を書いて知らせ、同じく止める。
- 1時間の関門（§4-3）の対象にはしない（PO 決定）。ただし測定の予約を**作る**ときは関門を通す（§4-3）。

### 4-3 1時間の関門（予約と定期実行）

- **変更前**: 重なりの検査は無い（R§1・R§2）。
- **変更後**:
  - 対象: AI が予約を作るとき、AI が定期実行を追加・更新・再開するとき、サーバーが測定の予約を作るとき（§4-4）。
  - 比べるもの:
    - pending の予約の開始時刻
    - 有効な定期実行の、これから366日の開始時刻（曜日と時刻から作る）
    - 更新のときは、更新する定期実行自身を比べる相手から外す。
  - 開始の差が60分未満のものが1つでもあれば拒む。日付をまたぐ差（23:30 と 00:10）も数える。
  - 拒むときの答えに、ぶつかった相手の名前と時刻、空いている一番近い時刻（前後それぞれ）を入れる。
  - 同時に2つの作成が来ても両方が通らないよう、予約と定期実行で**共通の1本の順番待ち**（createSerial、R§4 と同じ作り）の中で「比べる→保存する」を行う。
  - 「同じ1時間」は「開始の差が60分未満」と読む。PO が画面から作るものには関門をかけず、確認の欄で重なりを見せる（§14-2、PO 2026-10-21「1」）。
  - 既にある重なり（R§8）は便1 の導入のときに一覧にし、AI が作ったものは時刻をずらす（PO 決定の「時刻を変えてよい」の範囲）。
- 上限 `MAX_AGENT_PENDING=20` はそのままにする。
- 作りの細目（第13版。便1 のカードの元）:
  - 関門の部品を新しく1つ作る（A:server/schedule-gate.ts）。中身は、1本の順番待ち（A:server/json-store.ts の createSerial）と、重なりを調べる関数。配線（A:server/index.ts:76-77）で1つだけ作り、予約と定期実行の両方に渡す。今の予約と定期実行には、互いをまたぐ順番待ちが無い（予約は保存だけを並べる A:server/reservations.ts:86、定期実行は AI の操作だけを並べる A:server/routines.ts:110-117）。
  - 順番待ちに入れるのは、予約の作成と、定期実行の作成・変更・有効/無効の切り替えの全部（画面からも AI からも）。画面のものは比べないが、並べないと「AI が比べた直後に画面の作成が入る」ことは防げないため、並べる。関門で比べるのは AI のもの（`createdBy` が `agent`、定期実行は AI 用の受け口からの呼び出し）だけ。
  - 定期実行は、変更や切り替えのあとに有効になるものだけを比べる。無効にする操作は比べない。
  - 開始の時刻の作り方: 予約は `runAt`。定期実行は、今から366日のあいだの日本時間の各日のうち曜日が合う日の `timeHHmm`。比べる窓は「今」から366日。
  - 拒むときは、入力の誤りと同じ 400 で答え、文の中に、ぶつかった相手の名前・種類（予約/定期実行）・時刻と、空いている一番近い時刻（前後それぞれ）を入れる。ac-reserve と ac-routine はサーバーの `error` の文をそのまま出す（A:hooks/ac-reserve.mjs・A:hooks/ac-routine.mjs）ので、AI はこの文を読んで時刻を選び直せる。近い時刻は1分刻みで前後24時間まで探し、見つからなければ「なし」と書く。予約の前の時刻は「今から1分後」より前にしない（A:server/reservations.ts:17・172）。定期実行の近い時刻は、同じ曜日のまま `HH:mm` だけを動かして探す。
  - 測定の予約をサーバーが作る道（§4-4）は便3 で作る。便1 では、その入口が同じ関門の関数を呼べる形にしておく。
- 予約の監査記録（K6。第13版）:
  - 監査の置き場は定期実行と同じ1つのファイル（A:server/routine-audit.ts の routine-audit.jsonl）。記録の種類に `reserveCreate`・`reserveCancel`・`reserveDispatch` を足す（A:server/routine-audit.ts:11）。予約の id を入れる欄 `reservationId` を足す。画面からのものも AI からのものも残す（`targetCreatedBy` に `ui`/`agent`）。promptText などの本文は書かない（今の決まり A:server/routine-audit.ts:2）。
  - 書く部品は、配線で作られている1つ（A:server/index.ts:88 の routineAudit）を予約にも渡す。
  - 順番: 作成は「監査に `ok` を書く → 保存する」。監査に書けなければ保存せずに失敗にする。取消と開始は「メモリの状態を先に同期で書き換える → 監査に `ok` を書く → 保存する」（判定と書き換えの間に待ちを入れない。今の A:server/reservations.ts:201-203・:216-218 と同じ。先に監査を待つと、取消と開始が同時に来たとき、取り消した予約が開く。PR #70 の審査 H-1）。監査に書けなければ元の状態に戻して失敗にする（開始は、今の保存の失敗と同じく60秒あとにやり直す A:server/reservations.ts:219-224）。保存に失敗したら、監査に `denied`（`error` に保存の失敗）を書き足してから失敗にする（書き足せなければ画面の記録だけに出す）。
  - 予約の読み込みを待つことと入力の形の検査は、共通の順番待ちの外で先に済ませる（予約の読み込みが壊れたとき、定期実行の操作まで止めないため。PR #70 の審査 M-1）。ただし予約の一覧を読めていない間は、関門が重なりを確かめられないので、AI の予約・定期実行の作成・変更は拒む（重なりを見ずに通さない。拒む文に「続くなら PO に報告」を添える。PR #70 の審査 L-c・L-e）。
  - 関門・許可の一覧・「予約で選べない」で拒んだ作成と取消も `denied` で残す（入力の形の誤りの 400 は残さない。定期実行と同じ決まり A:server/http.ts:412-413）。

### 4-4 不具合の件の回・3回の不合格・全停止・報告

- **件の状態の正本は障害記録の表**（M-7）。
  - 状態は、行の `status` と、出来事の並び（`detail.round`）から決まる。手元の `discord-intake.json` は、起動したときに `GET /api/v1/ops/incidents/{id}` で読み直した写しで、判断の正本にしない。
  - 連続の不合格の数は、出来事 `result` の並びを数えて出す。手元で数えない。
- 回の進め方:
  1. 件の本体のセッション（`discord-case`）は、対策が済んだら `ac-case measure <件の id> --at <時刻> --criteria <200字>` を打つ。
     - 予約を作るのは**サーバー**。役割は `discord-measure` に固定、依頼文は §4-5 の測定の型に固定。件のセッションが役割や依頼文を選ぶことはできない。
     - §4-3 の関門の対象。
     - サーバーは予約を作ったあと、出来事 `measure` を書く。
     - **本体のセッションは、測定の予約が作られたら役目を終える**。サーバーは、本体のセッションが10分 idle になった時点で閉じる（§4-2 と同じ）。kept になったら閉じずに枠を持ち続けるので、測定は枠が空くまで開かない（§4-2 の「枠を通す」）。測定の時刻に本体を強制で閉じることはしない（判断待ちを飛ばさない）。
     - 測定の予約は、件の id と回を持つ（`reservations.json` の予約に `caseId`・`caseRound` を足す。今の `purpose` は `"measure"` だけ。A:server/reservations.ts:51,:67）。`createdBy` は `discord-intake` とし、AI の上限 `MAX_AGENT_PENDING=20`（:184）には数えない（`bug` の順番待ちの上限20と、1件につき pending の測定は1つまでの決まりで抑える）。
  2. 測定のセッション（`discord-measure`）が `ac-case result <件の id> pass|fail --note <200字>` を打つ。
     - 受け付けるのは、`ac-case` の合言葉が合い、かつサーバーがその回の測定予約から開いたと記録したセッションの名乗りのときだけ。
  3. 不合格なら、次の回の本体のセッションを `bug` の順番待ちに入れる。
- サーバーを起こし直したときの測定（L-4）: 送っている途中の予約は送り直されず `interrupted` になる（A:server/reservations.ts:146-148）。受け口は起動のときに、件の測定の予約が `interrupted` になっていたら、その測定を `bug` の順番待ちの先頭に入れ直し（予約は作り直さない）、出来事 `launch_failed`（`reason: 'interrupted'`）を書いて知らせる。同じ回で2回目の `interrupted` なら、入れ直さずに出来事 `stop`（`reason: 'unknown'`）で止める。
- **`ac-case` の認証**（H-B）:
  - `ac-case` 専用の合言葉 `dataDir/case-token`（0600）を作る。reserve-token とは別にする。`ac-case` の入口は reserve-token を受けず、ac-reserve・ac-routine の入口は case-token を受けない。
  - サーバーは、合言葉に加えて次をすべて照合する。合わなければ拒む。
    - 名乗り（`CLAUDE_CODE_SESSION_ID`）が、受け口が今「動いている」と記録しているセッションのどれか。
    - 操作がその名乗りの役目に合う: `measure`・`note` は今の回の本体だけ、`result` は今の回の測定だけ、`halt` は誰でも（止める向きだけなので）。
    - 件の id がそのセッションの件と同じ。
  - `note` で書けるのは `root_cause`（2000字まで）・`fix_pr`（整数）・`needs_action`（真偽）の3つだけ。ほかの名前が来たら 422（M-F）。保守 API の側は KGI 5 を守る欄（`ai_started_at`・`detection_path`・`first_aid_*`）を拒む（§4-9）。
- **名乗りと合言葉の弱さ**（H-3・H-B）:
  - 照合は `checkRoutineCaller`（A:server/http.ts:402-408）と同じく、フックが送るセッションの id を信じる形で、本人の確かめではない。会話の id は `~/.claude/projects/` のファイル名から読める（第4版の審査の実測）。0-13 で、名乗り（`CLAUDE_CODE_SESSION_ID`）・agent-console が開いたセッションの記録の `claudeSessionId`・`claude agents --json` の `sessionId` が同じものを指すと確かめた（記録の10件すべて一致）。記録の `id` はアプリ側の別の番号なので、照合には `claudeSessionId` を使う。
  - agent-console と Discord 発のセッションは、同じ Mac の同じ利用者として動く。そのため、`node -e` や `python -c` のような子プロセスを使えば、case-token・reserve-token・`~/.claude-access.env`・`~/.claude/channels/` 配下の `.env` を読むことを、起動の引数の道具の拒否では塞げない（`--settings` の permissions の拒否は道具の型にしか効かない）。ただし、サンドボックスの `filesystem.denyRead` に入れた試験用の置き場（/tmp 配下）は、子プロセスの `cat`・`python3` でも読めないと 0-15 で確かめた（§4-5）。ホーム配下の本物の置き場・ほかの子プロセス・Grep など Read 以外の道具で同じく塞がるかは【未確認】（便2 の K11・K13 の試験で確かめる）。一覧に入れていない置き場と、`ac-case` のために一覧から外す case-token は読める。K11・K13 は「道具の型で読めない」までを保証し、この道は ADR-1039 に弱い点として書く。
  - 被害を小さくする作り:
    - 不具合の枠は1つで、kept でも空けない（§4-2）。測定が開いているとき、不具合の種類のほかのセッションは生きていない（K14）。
    - case-token でできることは、今の件・今の回の操作だけ（上の照合）。
    - ac-reserve は許可する役割の一覧で絞り（§4-5）、AI の予約と定期実行の作成・変更は1時間の関門と監査記録を通る（§4-3、K5・K6）。
    - 検出: Discord 発のセッションが1つでも動いている間に、ac-reserve での予約の作成・取消、ac-routine での定期実行の追加・更新・再開があったら、サーバーは報告チャンネルに「確認してください（Discord の件が動いている間に予約・定期実行が変わりました）」を出し、出来事 `suspicious` を書く（K16）。不具合の件が動いていない（誤り報告のセッションだけが動いている）ときは、障害記録に書く行が無いので、知らせと agent-console の監査記録（`suspicious`）だけにする（§4-6）。
    - 投稿できる人を PO だけに絞る（§14-1）。
  - 切り離されたプロセスの残り（M-4）: `sessions.close` が終わらせるのは端末とその子孫だけ（A:server/sessions.ts:506-507）。本体のセッションが `nohup`・`setsid` などで親から切り離したプロセスは、本体を閉じても残りうる。そのプロセスは case-token を読め、測定のセッションの会話の id も `~/.claude/projects/` から読めるので、測定を名乗って `ac-case result pass` を送れる（対策を作った本体が自分で合格を付けられる）。
    - 対策（見張り）: 起動関数は件のセッションに印の環境変数 `AC_DISCORD_CASE=<件の id>:<回>` を付ける。サーバーは測定を開く直前に、値を問わず `AC_DISCORD_CASE` を持つプロセスが残っていないかを調べる（前の回の本体が残したものも測定を名乗れるため）。残っていれば測定を開かず、出来事 `stop`（理由 `leftover`）と `suspicious` を書いて知らせ、PO の判断を待つ。macOS で同じ利用者のプロセスの環境変数を読めるか（`ps -E` など）は第0段 0-14 で確かめる【未確認】。読めないと分かったら、この対策は外して PO に戻す。
    - 限界: 印の環境変数は、そのプロセスが自分で消せる。見張りは「うっかり残ったもの」を見つけるもので、わざと隠したものは見つけられない。
  - 残る弱さ（同じ利用者のファイルが読める。外への通信は許可した行き先に絞る作りだが、許可外の行き先への7つの道が拒まれることは 0-15 で確かめた。許可した行き先へは書ける（§4-5・K17）・誤り報告の種類のセッションや普通のセッションが名乗れる・切り離されたプロセスが測定を名乗れる。0-14 により見張りは作れない前提）を、この形で受け入れるかは PO に確かめる（§14-8）。PO の答え（2026-10-21）: 「1で進めて試す」のあと、0-20 の結果を受けて「変えるなら2,まず3だけで動作確認と試験をしつつ穴を塞ぐ」。→ 同じ利用者のまま、最初は PO だけが投稿し、試験で穴を塞ぎながら進める。作りを変えるときは、Discord 発のセッションを別の macOS の利用者で動かす（§5 案H）。
- 3回続けて不合格なら、その件の自動の回は止まる。出来事 `stop`（理由 `failed-3`）を書き、行は `firing` のまま残し、報告チャンネルに知らせる。PO の判断を待つ。
- 測定の予約の時刻から24時間たっても結果が無いときは、出来事 `stop`（理由 `unknown`）を書く。不合格には数えず、知らせて止める（推測で合否を付けない）。本体が kept のまま24時間を超えて枠を持ち続け、測定が開けなかったときも、この決まりで `unknown` で止まる（その間「判断待ち」「長くかかっています」は出続ける）。
- 合格なら、`POST /api/v1/ops/incidents/{id}/close` で `resolved` にする。**`resolved` にするのは合格のときだけ**（M-3。止めた件を「片付いた」と数えないため）。
- 全停止: 新しいスイッチは作らず、既存の `public.ops_control.halt_all`（ADR-1012 段階2。R§11）を使う。`bug` の起動が見る。`error-report` の起動も見る（§14-7、PO 2026-10-21「1」。誤り報告を止めたあと戻せるのは super admin のログインだけ。S:backend/app/routers/ops.py:483-489）。
  - 読み方: サーバーが起動の直前（新しい件・次の回・測定の予約の作成と起動）に毎回、`GET /api/v1/ops/control` を読む。
  - 読めないとき（本番が落ちている・鍵が無い・鍵が違う）は「止まっている」とみなして起動しない。投稿は順番待ちに残し、報告チャンネルへ「全停止の状態が読めない」を知らせる。
  - 止める方法: 既存の `POST /api/v1/ops/control/halt`（鍵で止められる）。agent-console からは `ac-case halt` と画面のボタンの2つの入口を作り、どちらもこの API を呼ぶだけにする。
  - **再開は既存の `POST /api/v1/ops/control/resume` だけ**。super admin のログインが要り、鍵では戻せない（R§11）。agent-console に再開の入口は作らない。
  - 再開を知る方法（M-4）: 止まっている間、または読めない間は、60秒ごとに状態を読む。止めが外れた（false が読めた）ら、報告チャンネルに「再開を確認」を出し、順番待ちから続ける（K8）。
  - 止まっている間、pending の測定予約は取り消し（`reserveCancel`、理由 `halt`）、出来事 `stop`（理由 `halt`）を書く。再開しても自動では予約し直さず、件ごとに報告チャンネルへ「再開待ち」を出す。
  - 画面のボタン（「全停止」と、`launch_failed` で止まった件の「やり直す」）は、件の一覧の枠に置く。部品は既存の金型を使い、文言は t() を通す（agent-console の i18n。R§9）。色・大きさの直書きはしない（A:scripts/check-design-governance.mjs が lint で止める）。
- 報告チャンネルに送る知らせ:
  - 受け付けました／開始／遅れました（N分）
  - 合格／不合格（第n回）／3回不合格で停止
  - 全停止を確認／再開を確認／状態が読めない
  - 判断待ち（`NEEDS_DECISION:` か `BLOCKED:` で止まった。答える場所は agent-console の画面のそのセッション。待っている件の数を添える）／長くかかっています（8時間ごと）
  - 異常（取りこぼしの可能性、本番ボットの id と同じ、開けなかった、記録に失敗、結果が無い）
  - 確認してください（Discord の件が動いている間に予約・定期実行が変わった。K16）
  - 誤り報告の件の知らせは ADR-1025 の決まり（誤り報告チャンネルのスレッドに書く）のままで、本設計は足さない。
- 本文には、件の日時・投稿へのリンク・短い状態だけを書く。投稿の本文は書き写さない（社外秘を広げない）。
- 遅延の判定: 投稿の時刻から「受け付けました」までが5分を超えたら「遅れました（N分）」を出す（K9）。
- Webhook の送信に失敗したら、30秒・2分・10分で3回やり直す。それでも失敗したら macOS の通知（R§4）で知らせ、出来事 `notify_failed` を書く。

### 4-5 役割 `discord-case`・`discord-measure` と依頼文

- **ツールを起動の引数で絞る**。手元の claude 2.1.305 のヘルプに、`--disallowedTools`・`--tools`・`--settings`・`--strict-mcp-config` がある（R§10）。第0段 0-4（claude 2.1.308）で次を実物で確かめた（結果は各項の →）。
  - `--disallowedTools` で WebFetch・WebSearch を外せるか。→ 道具の一覧から消えた。
  - `Bash(curl *)`・`Bash(wget *)`・`Bash(security *)`・`Bash(gh pr merge *)` の形で拒めるか。auto の許可モードでも効くか。→ curl・wget・`security` は、dontAsk・auto の両方で `--disallowedTools` の拒否で、dontAsk で `--settings` の permissions の拒否でも拒否された（auto ＋ `--settings` は試していない【未確認】）。ただし `/usr/bin/curl`・`bash -c` 経由・`/usr/bin/security` は名前の形の拒否をすり抜けて動いた（`env curl` だけは拒否。抜け道の試験は dontAsk ＋ `--disallowedTools` の条件だけで行った）。名前の形の拒否は守りにならないので、外への通信はサンドボックスの行き先の許可（0-15）で、Keychain と秘密の置き場は 0-5 の作りで塞ぐ（K13 から外した）。`gh pr merge` は dontAsk・`--disallowedTools` の名前の形の拒否で止まった（auto・`--settings` は利用者の設定の見張りが先に止めたため【未確認】）。`bash -c` 経由は利用者の設定の見張りが先に止めたため分けて確かめられず、絶対パスの道は試していない【未確認】（K13 の補助の扱い。§2）。試験の条件（p004.sh）: dontAsk の回はどれも `--allowedTools` に Bash を入れた（対照の R0 は `Bash WebFetch`、サブエージェントの回は `Bash Agent`）。auto の回（R2）は `--allowedTools` を付けていない。`gh pr merge` の名前の形の拒否を見張りと分けて確かめた回（R7・R7c）は、`--setting-sources project` で利用者の設定を読まずに動かした。本番の起動は利用者の設定を読むので、便2 でその条件のまま確かめ直す。その条件では利用者の設定の見張りが先に止める見込みなので、§9 の K13 の受入（すべて拒否）はどちらの拒否でも判定し、どちらが止めたかを記録に書く。wget はこの Mac に入っていないので、何もしない見本（p004/bin/wget）を PATH の先頭に置いて試した。「wget は拒否された」は、名前の形の拒否が見本に効いたという意味。サブエージェントに制限が効いたと確かめたのは dontAsk ＋ `--disallowedTools` の回（R4）だけで、auto と `--settings` の条件では試していない【未確認】。
  - 本体のセッションが呼ぶ Sonnet の担当（サブエージェント）にも同じ制限が効くか（U8）。→ 効いた（サブエージェントでも拒否）。制限の無い対照で通ったと言えるのは curl・wget・`security`・ac-reserve。`gh pr merge` と ac-routine は対照でも利用者の設定の見張りが先に止めたため、サブエージェントで制限そのものが効いたかは分けられていない【未確認】。
  - 次の置き場への Read と Bash の `cat` を `--settings` の拒否で塞げるか（permissions の拒否は道具の型まで。permissions の拒否だけでは子プロセスでの読み取りは塞げない。§4-4）: agent-console の dataDir（reserve-token を含む。case-token は `ac-case` が読むので拒否の対象から外す）、`~/.claude-access.env`（保守 API の鍵の平文。R§11）、`~/.claude/channels/` 配下の `.env`（ADR-1009 のトークンの平文。R§6）（H-4）。→ 0-15 で、試験用の置き場（/tmp 配下）について、Read は `Read(//<絶対パス>/**)` の書き方で、Bash の子プロセスの `cat`・`python3` はサンドボックスの `filesystem.denyRead` で塞げると確かめた（下の「読み取りの拒否の書き方」）。上の本物の置き場では便2 の K11・K13 の試験で確かめる【未確認】。→ 0-5 で、試験用の Keychain の項目と試験用の平文の置き場は、権限の拒否とサンドボックスの `filesystem.denyRead` を両方付けた作りでは、Read・`cat`・`python3`・`security`・`python3` から `security` を呼ぶ道のどれでも値が出なかった（`security` を直接打つ道は権限で拒否。`python3` から `security` を呼ぶ道は「項目が無い」の終了コード 44 で、項目は在った）。権限の拒否だけでは `python3` の読み取りと `python3` から `security` を呼ぶ道で読めた。Read の道具はサンドボックスでは塞がらず、Read の拒否が別に要る。Keychain を隠したのが denyRead かサンドボックス全体かは分けていない【未確認】。
  - ac-reserve・ac-routine を拒めるか（役割の照合でも塞ぐ。下記）。→ 名前の形の拒否は dontAsk・auto の両方で効いた。抜け道（絶対パス・`bash -c`）は試していない【未確認】ので補助とし、塞ぐのは下の役割の照合にする。
- サーバー側で塞ぐもの:
  - ac-reserve（AI の予約）は、**許可する役割の一覧**に入っている呼び出し元だけを通す。呼び出し元の名乗りが無いときは拒む（H-3）。今は役割を見ていない（A:server/http.ts:364-371）。一覧は、今 ac-reserve を使っている役割を第0段 0-11 で数えてから決める（今動いている予約を壊さないため）。

    - 0-11 で数えたのは予約が**開く**役割（予約の `roleId`）で、呼び出した側の役割は記録が無いので数えられなかった【未確認】。呼び出した側は名乗りを付けたあとの監査記録（`reserveCreate`）で分かる。導入のあとに監査記録を見て、一覧から外れて拒まれた呼び出しがあれば PO に伝える。
  - `discord-case`・`discord-measure` は一覧に入れない。2つとも、ac-reserve でも画面の予約の役割の選択肢でも選べないようにする（L-c）。
    - 役割の設定に「予約で選べない」の印 `reservable: false` を足す（型の検査は A:server/config.ts:137-158）。
    - 画面の予約の入口（A:server/http.ts:196）と ac-reserve の入口は、この印の役割を 400 で拒む。
    - 画面の選択肢（A:src/components/Reservations/ReservationEditor.tsx:41 の `roles.map`）から、この印の役割を外す。

### 4-7 落ちたら起こし直す見張り役

- **変更前**: KeepAlive=false。落ちたら、Dock のアプリを人が開くまで止まったまま（R§5）。
- **変更後**: 別の LaunchAgent `local.agent-console.watchdog` を足す。
  - 30秒ごとに /healthz を読み（待ちは5秒）、2回続けて応答が無ければ `launchctl kickstart -k gui/<uid>/local.agent-console.server` を打つ。落ちてから起こすまで最大65秒。起動に要る時間を足して K12 の120秒に入るかを便5 の受入で測る。
  - 導入・更新・切戻し・外す台本は、作業の初めに `dataDir/maintenance` という印を置き、終わったら消す。途中で失敗しても消えるよう `trap` で消す。印がある間、見張り役は起こさない。印が30分を超えて残っていたら、起こさずに報告チャンネルへ知らせる。
  - 見張り役が起こした回数を監査記録に残す（`watchdogKick`）。10分に3回を超えたら起こすのをやめ、知らせる。
- 比べた案: KeepAlive の `SuccessfulExit=false`。**採らない**（0-6 の結果で決めた）。理由は2つ。
  - 止め方の実物（A:scripts/lib/ac-common.sh:226-236）は `launchctl kill SIGTERM` で止め、pid が消えるのを約10秒待ち、消えなければ終了コード1で中止する。SIGTERM で止まったサーバーを launchd が「成功の終わり」と見るかは確かめていない【未確認】。見なければ、更新の台本が止めた直後に launchd が起こし直し、pid が消えず台本が中止する恐れがある。
  - 手元の `man launchd.plist` の SuccessfulExit は「終了の状態で起こし直す」もので、終わらずに応答だけが止まった状態は拾わない。見張り役は /healthz の応答で見るので、その状態も拾う。

- **変更前**: 障害記録の行を作れるのは Alertmanager からの受け口（S:backend/app/routers/ops.py:213）だけ。出来事の入口（:357）は `kind`・`note`（2000字）・決まった列の `fields` だけを受け、`detail` は `{fields, note, user_id}` に固定（:395-397）。回の中身を入れる欄が無い（H-2）。
- **変更後**: 表の形（列・制約）は変えない（migration 無し）。
  - `POST /api/v1/ops/incidents/human`（保守の鍵）: 人の報告から1行を作る。
    - `fingerprint='discord:<投稿の id>'`、`starts_at`・`first_notified_at`・`last_notified_at`・`human_noticed_at` = 投稿の時刻（M-2。2つの通知の時刻は NOT NULL で既定値が無い。S:mig.sql:14-15）、`alertname='discord-bug-report'`、`detection_path='human'`、`status='firing'`、`labels` = `{source:'discord', message_url, test?}`。本文は入れない。
    - 同じ `fingerprint`・`starts_at` が既にあれば、作らずに既存の行を返す（一意の制約 :31）。答えに `inserted`（true/false）を入れる。
    - `inserted=true` のときだけ、出来事 `accept` を1行足す（`kind='notified'`、`detail.round = {step:'accept', n:1, at}`。人の報告を受けた、の意味で既存の値を使う）。
  - `POST /api/v1/ops/incidents/{id}/close`（保守の鍵）: `status='resolved'`・`resolved_at` を入れ、出来事 `result`（pass）を1行足す（`kind='resolved'`、`detail.round = {step:'result', result:'pass', n, session_id, at}`）。`labels.source='discord'` の行だけを受ける（Alertmanager の行を閉じない）。
  - 既存の出来事の入口（:357）に、省略できる `round` を足す。`detail` を作る場所（ops.py:395-397）で `detail.round` に入れる。中身は決まった名前だけ（`extra="forbid"`）:
    - `step`: start / launch_failed / kept / closed / measure / result（fail）/ stop / notify_failed / suspicious（この入口では `kind='ai'` で書く。accept と result の pass は上の2つの入口が書く）
    - `n`（回。1〜99）・`session_id`（64字まで）・`reservation_id`（64字まで）・`result`（pass / fail）・`reason`（failed-3 / unknown / halt / interrupted / lost / full / not_ready / failed / cwd_invalid / needs_decision / blocked / waiting_60m / no-reply / leftover のどれか。no-reply は受け口の見張りが、10分 idle になったのに最後の返答が読めないセッションを kept にするとき。routine-closer の同じ判定（A:server/routine-closer.ts:78）を共通の関数として使う）・`at`（時刻）
  - 大きさ（L-2）: `detail` は表の制約で 8192 バイトまで（S:mig.sql:58）。超えると DB の制約違反で 500 になるので、入口で `detail` を作ったあとに JSON の大きさを測り、8000 バイトを超えたら 422 で返す。`round` があるときの `note` は 500 字までにする（日本語でおよそ 1500 バイト）。
  - Discord 発の行の欄の絞り（M-F）: 既存の入口は `fields` で `ai_started_at`・`detection_path` なども書ける（S:backend/app/routers/ops.py:43-54,:341-346）。`labels.source='discord'` の行には、`fields` の `ai_started_at`・`detection_path`・`first_aid_started_at`・`first_aid_done_at`・`first_aid_result` を 422 で拒む（K15 の「`ai_started_at` が空」をこの入口で保証する）。保守 API は鍵の持ち主を見分けられない（S:backend/app/routers/ops.py:361 は同じ入口）ので、3欄だけに絞ると振り返りの `review_note`・`human_noticed_at` まで誰も書けなくなり、ADR-1012 KGI 6 の振り返りが作れない。そのため API の側は「拒む欄の一覧」にし、3欄だけの絞りは agent-console の `ac-case note` の側でかける（M-3）。
- `round` を足すのは既存の入口の型の拡張で、今の呼び出し元（ADR-1012 の段階2 の利用）は省略するので変わらない。
- 3つとも `halt_all` が true でも記録を続ける（S:docs/handoff/ai-ops-247/stage2-design.md:177）。止まっている間に起動しないのは agent-console の側の役目（§4-4）。

## 5. 代替案と選んだ理由

| 案 | 内容 | 採否と理由 |
|---|---|---|
| A | agent-console のサーバーの中で Gateway に常時つなぐ（第3版の形） | 採らない。ADR-1025 が REST の読み取りで PO 承認済みで（S:ADR-1025 Decision 4）、受け口を1つにするには読み方を揃える必要がある。常時接続は、切れて戻ったときの合図（U7）を確かめないと補完が作れない |
| B（採用） | REST で30秒ごとに読む。2つのチャンネルを1つの部品で読む | ADR-1025 と同じ作りで1つにまとまる。`after` で「最後に処理した投稿より後」を読むので、止まっていた間の投稿も同じ仕組みで拾える。5分以内（K1・S:kgi.md:12）に30秒は収まる |
| B' | 誤り報告と不具合で受け口を別々に作る | 採らない。Discord を読む通信と、チャンネルごとの最後の id の置き場が2つになり、正本が分かれる（全停止は §14-7 の答えで共通にした） |
| C | ADR-1009 の常駐 Claude Code の受付を立て直す | PO が「claude と discord を繋ぐのではなく」と言っている |
| D | 受け口を別のプロセスにする | 状態の置き場が2つになり、正本が分かれる |
| E | KeepAlive=true にする | 導入の台本とぶつかる（R§5）。`SuccessfulExit=false` は §4-7 で比べる |
| F | 件の記録と全停止を agent-console の手元に持つ | 本番の障害記録の表と全停止が既にあり（R§11）、二重になる |
| H | Discord 発のセッションを、別の macOS の利用者で動かす（ファイルの読み取りを OS で分ける） | 今は採らない。agent-console は1人の利用者の tmux でセッションを動かす作りで、利用者を分けるには起動・画面・権限の作りを大きく変える。同じ利用者のまま、被害を小さくする作り（§4-4）と検出（K16）で進めるかを PO に聞き（§14-8）、受け入れられないときにこの案を設計する |
| I | kept で枠を空ける・測定の時刻に kept の本体を強制で閉じる（第4版の形） | 採らない。kept の本体が生きたまま次の件が開き、測定の名乗りの相手が残る（第4版の審査 H-A）。強制で閉じると PO の判断待ちを飛ばす |
| G | 件の番号 `DC-NNNN` を行の数から振る（第3版の形） | 採らない。同時に2件来ると同じ番号になりうる。番号のために表を変える（migration）のは見合わない。行の id を鍵にし、人に見せる名前は投稿の日本時間にする |
